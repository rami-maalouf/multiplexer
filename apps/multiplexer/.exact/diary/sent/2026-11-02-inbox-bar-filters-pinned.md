### Rough
- The app is checked out twice (a second git worktree, so two agents can build at once), and its build folder (`target/`) was copied from the first checkout to save the first build. `ios` then failed after cargo finished: "no matching rustc unit dep-info for unicode_ident; searched target directory <second checkout>/target; rebuild the stale Cargo unit or use a private target directory". The dep-info files hold the first checkout's absolute paths. After I rewrote those paths, Swift failed next: "precompiled file '.../webarm-module-cache/.../SwiftShims-....pcm' was compiled with module cache path '<first checkout>/...', but the path is currently '<second checkout>/...'". Deleting the four `*-module-cache` folders under `target/apple-swift/` fixed it. Cost about 8 minutes. What would have helped: the first message naming which folder to delete (or the build noticing a moved `target/` and rebuilding those units by itself); the message's "rebuild the stale Cargo unit" did not say how.
- `fn f(x: string): string = match x { case "unread" => "Unread", case _ => "All" }` failed with "expected `some`, found a string" at each string pattern. I had read `match` as a general switch; the message does not say that `match` takes only an option, or what to write for a string (a chain of `? :`). Cost about 3 minutes. What would have helped: the refusal saying "match takes an option; for a value, write `x == "a" ? … : …`".
- A floating bar is a `row position="absolute"` across the screen with only its buttons taking touches, so I wrote `pointer-events="none"` on the row and `"auto"` on each button (React Native's `box-none` is refused, with a clear list of values). The bar's pull-down menu (a `popover` column inside that row) then could not be tapped in a drive: "tap #116 at (75.83, 663.83): node #90 covers its middle", node #90 being a list row under the painted menu. The cause was the popover inheriting `pointer-events: none` from the row, as CSS does; `pointer-events="auto"` on the popover fixed it. Cost about 4 minutes. What would have helped: the refusal naming the inherited `pointer-events: none` on the target (the agent knows it), not only the node that covers it.

So the bar is `position="absolute"`, the list's last row clears it with `padding-bottom`, and the rows pass under the glass with no scroll edge effect. To check, I tried the other shape LLP 1131 describes: an inline title and the same bar in flow after the list. The list did run under the bar (so it took a band), but a capture of the simulator's display (iOS 26.5, dark, also with `-exact-scroll-edge-effect="soft"` on the list) showed no edge effect either: the rows under the bar stayed sharp. I went back to the large title. Cost about 25 minutes, mostly reading `ControlBarsIOS.swift` and `PageEdgesIOS.swift` to learn why. What would have helped: a bottom toolbar a route can name (iOS's `toolbarItems`, which keeps the large title and draws the edge effect), or a line in the glass docs saying which floating bar gets the edge effect and which does not.

- A floating bar's round `buttonStyle="glass"` button with only a symbol: at the largest accessibility text size its symbol grew past the 48-point circle (UIKit's bars keep theirs fixed). `font="-exact-title3"` on the `image` was refused: "a native button's `image` takes no `font`; ... A native button's face is `text`s and a symbol `image`, sized by `font-size`". I read that as `font-size` on the button, wrote it there, and the build took it with no warning and no effect. `font-size=20` on the `image` works. Cost about 6 minutes and two drives. What would have helped: the refusal saying "write `font-size` on the image", and a warning for a `font-size` on a native button whose face has no `text`.
- Then `verify ios` flagged those symbols as fixed type ("`image font-size=20`: stays 20 pt as Dynamic Type grows; a role ... or a `rem` size scales"). A role made them overflow the circle again, so I wanted a capped size: `font-size="min(1.2rem, 24px)"` on the image is refused ("expected number"), though the same `min()` works on a `text`. `exactPage()` has no root font size (the bake listed what it answers), so the symbols now take 20 or 24 from `exactViewport().accessibilityTextSize`. Cost about 10 minutes. What would have helped: an image's `font-size` taking the `min()`/`rem` forms a text takes, or the fixed-type finding naming a capped form that fits a fixed control.
